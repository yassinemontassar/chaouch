# Workflows

Practical steps for the owner. Commands run from the repo root in PowerShell.

## 1. Adding an official document

1. Add an entry to `data/documents/sources.yaml`:

   ```yaml
   - doc_id: doc_cin_03            # stable, lowercase; gold questions reference it. Never reuse an id.
     url: "https://..."
     procedure: cin                # one of the 5 procedures (spec 3.3)
     language: fr                  # fr or ar
     license_note: "Footer: '...'. No terms-of-use page found."
     notes: "May predate the 2024 CIN law."   # optional: your caveats about the page
     extract_mode: recall          # optional, HTML only: default precision; use recall if text is missing
   ```

   Prefer HTML pages over PDF forms: fill-in forms extract as scrambled Arabic (ADR 0006).
2. `uv run tasks.py ingest`. Already downloaded pages are skipped (`uv run tasks.py fetch --force` re-downloads).
   A site that blocks us or fails is reported; don't work around it.
3. Read `data/documents/processed/<doc_id>.md`. Check that the conditions, required documents, fees and
   delays are all there and that the Arabic reads normally. If a block is missing, set `extract_mode: recall`
   and run `uv run tasks.py clean` and `uv run tasks.py chunk` again.
4. From Phase 1: re-run the indexing step so retrieval sees the new chunks.

`processed/` is regenerated by ingest and is not committed (copyrighted text); commit `sources.yaml` only.

## 2. Adding or changing gold questions

The spreadsheet `chaouch_gold_questions.xlsx` (tab "Questions") is the source of truth; `questions.jsonl` is
generated from it, so edit the spreadsheet, not the JSONL.

1. Edit the spreadsheet. Keep row 2 as the EXAMPLE row. Use real `doc_id`s in `gold_doc_ids`, and separate
   `required_facts` and `gold_doc_ids` with `;`.
2. `uv run scripts/gold_from_xlsx.py ../chaouch_gold_questions.xlsx`
3. `uv run tasks.py validate-evals`. Errors name the JSONL line; line N is spreadsheet row N+2.
4. Bump the gold-set version (below), update the Provenance section in `data/evals/gold/README.md` if the
   way questions were written changed, and commit.

### Gold-set versions

- **v1** = the current 51 questions (2026-10-11).
- Any change to questions, answers, facts or doc ids makes a new version (v2, v3, ...). Typo fixes count too:
  they can change scores.
- Every report records the version it was run on, and numbers are only compared within the same version.
  After a new version, re-run the baselines you want to compare against.

Proposed recording (not implemented yet): a `version: v1` field under `gold:` in `configs/eval.yaml`. The
runner copies it, the question count and the sha256 of `questions.jsonl` into every report JSON, and prints
"Gold set v1 (51 questions)" in the Markdown table. If the hash differs from the one recorded for that
version in the gold README, the runner warns that the file changed without a version bump.

## 3. Running evaluations on free tiers

| Command | What it runs | Cost |
|---|---|---|
| `uv run tasks.py eval-smoke` | B2 on the first 20 in-scope questions | about 20 answers + 60 judge calls |
| `uv run tasks.py eval-full` | every system in `configs/eval.yaml` on all in-scope questions | about 260 answers + 690 judge calls |

Use `--systems B0_qwen,B3` to run only some systems. Ollama must be running for B0/B1.

**Daily re-runs.** Free tiers have daily limits (the judge's 200K tokens/day on Groq is the tightest).
When a limit is hit, the run stops those questions with a `quota:` error and marks the report incomplete.
Run the same command again the next day: everything already done comes from the cache, and only the
missing calls are made. Repeat until the report shows 0 errors. Limits live in `configs/models.yaml`;
update them from the providers' consoles when they change.

**The eval cache** is a SQLite file at `C:\dev\cache\chaouch\eval_cache.sqlite` (`cache_path` in
`configs/eval.yaml`), outside the repo and OneDrive. It stores every answer and judge call, keyed by the
provider and the exact request (model, prompt, parameters). The same request is never paid twice; a changed
prompt or model makes new calls. It is for development runs only; the app never uses it. It is safe to
delete, but the next run makes every call again.

**Reports** go to `reports/`: `<date>_<system>.json` (per-question results) and `<date>_baseline.md` (the
table). Smoke reports are ignored by git. Commit only the reports of a complete full baseline; the date is
the day of the final, complete run.

## 4. Choosing the main local model after the baseline

Do the judge calibration (spec 8.2, ADR 0007) first, then compare Qwen3.5 2B and Falcon-H1 3B in this order:

1. **B1 correctness and dialect**: the closest to how Chaouch will be used (model + documents).
2. **Latency** (p50/p95) on the laptop GPU, with a 4096 context.
3. **Fine-tuning support**: QLoRA with Unsloth/PEFT on Kaggle, and export back to GGUF (spec Phase 4).
   Falcon-H1's hybrid architecture needs checking.
4. **B0**: what the model knows without documents; a tie-breaker.

Look at the by-script breakdown too: a model that fails on Arabizi is a poor fit even with a good average.
Record the choice and the numbers in an ADR.
