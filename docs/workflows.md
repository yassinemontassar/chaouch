# Workflows

Practical steps for the owner. Commands run from the repo root in PowerShell.

## 1. Adding an official document

1. Add an entry to `data/documents/sources.yaml`:

   ```yaml
   - doc_id: doc_cin_05            # stable, lowercase; gold questions reference it. Never reuse an id.
     url: "https://..."
     procedure: cin                # one of the 5 procedures (spec 3.3)
     language: fr                  # fr or ar
     license_note: "Footer: '...'. No terms-of-use page found."
     notes: "May predate the 2024 CIN law."   # optional: your caveats about the page
     extract_mode: recall          # optional, HTML only: default precision; use recall if text is missing
   ```

   Prefer HTML pages over PDF forms: fill-in forms extract as scrambled Arabic (ADR 0006).
2. `uv run tasks.py ingest`. Already downloaded pages are skipped (`uv run tasks.py fetch --force` re-downloads).
   A site that blocks us or fails is reported; don't work around it.
3. Read `data/documents/processed/<doc_id>.md`. Check that the conditions, required documents, fees and
   delays are all there and that the Arabic reads normally. If a block is missing, set `extract_mode: recall`
   and run `uv run tasks.py clean` and `uv run tasks.py chunk` again.
4. Rebuild the retrieval index: start Docker Desktop, then `uv run tasks.py db-up` and
   `uv run tasks.py index` (embeds every chunk with each model in `configs/retrieval.yaml`, ~1 min on CPU).
   Retrieval and `eval-retrieval` refuse to run on an index older than `chunks.jsonl`.
5. A **distractor** (`role: distractor`, `procedure: other`) is an official page on another procedure,
   indexed only to make retrieval harder (ADR 0013). It must not answer any gold question: run
   `uv run python -m scripts.distractor_check` and read the flagged pairs before keeping it.
6. The **same page in the other language** (e.g. the Arabic version of a French page) gets
   `translation_of: <original doc_id>` (ADR 0014). Gold questions keep naming the original in
   `gold_doc_ids`; `eval-retrieval` counts a chunk from either version as the gold document. Both must be
   core documents of the same procedure, in different languages. Check the facts match before adding it.

`processed/` is regenerated by ingest and is not committed (copyrighted text); commit `sources.yaml` only.

## 2. Adding or changing gold questions

The spreadsheet `chaouch_gold_questions.xlsx` (tab "Questions") is the source of truth; `questions.jsonl` is
generated from it, so edit the spreadsheet, not the JSONL.

1. Edit the spreadsheet. Keep row 2 as the EXAMPLE row. Use real `doc_id`s in `gold_doc_ids`, and separate
   `required_facts` and `gold_doc_ids` with `;`.
2. `uv run scripts/gold_from_xlsx.py ../chaouch_gold_questions.xlsx`
3. `uv run tasks.py validate-evals`. Errors name the JSONL line; line N is spreadsheet row N+2.
4. Bump the gold-set version (below), update the Provenance section in `data/evals/gold/README.md` if the
   way questions were written changed, and commit.

### Gold-set versions

- **v1** = the current 51 questions (2026-10-11).
- Any change to questions, answers, facts or doc ids makes a new version (v2, v3, ...). Typo fixes count too:
  they can change scores.
- Every report records the version it was run on, and numbers are only compared within the same version.
  After a new version, re-run the baselines you want to compare against.

Proposed recording (not implemented yet): a `version: v1` field under `gold:` in `configs/eval.yaml`. The
runner copies it, the question count and the sha256 of `questions.jsonl` into every report JSON, and prints
"Gold set v1 (51 questions)" in the Markdown table. If the hash differs from the one recorded for that
version in the gold README, the runner warns that the file changed without a version bump.

## 3. Running evaluations on free tiers

| Command | What it runs | Cost |
|---|---|---|
| `uv run tasks.py eval-smoke` | B2 on the first 20 in-scope questions | about 20 answers + 60 judge calls, ~20 min |
| `uv run tasks.py eval-full` | every system in `configs/eval.yaml` on all in-scope questions | about 260 answers + 690 judge calls, ~3 h |

Smoke is a quick check that the pipeline works after a change; only full runs give comparable numbers.
Use `--systems B0_falcon,B3` to run only some systems. Ollama must be running for B0/B1.

**The judge** is Gemma 4 31B on Google AI Studio (`gemma_judge`, ADR 0010), with the same `GEMINI_API_KEY`
as B2. Free tier: 14.4K requests/day and 16K *input* tokens/min. The tokens/min limit binds: the
faithfulness prompts carry the documents (~4K tokens), so the judge runs at 3 requests/min. Each call
takes ~30 s because Gemma always thinks first. `groq_judge` (gpt-oss-120b, 200K tokens/day) is kept for
re-runs; switch `judge_model` in `configs/eval.yaml` to use it.

**Re-run until 0 errors.** A failed call is never cached, and the run keeps going: the report lists the
failed questions (`quota:` for a rate limit, or a 500/503 from a busy API) and is marked incomplete. Run the
same command again: everything already done comes from the cache and only the failed calls are made. The
2026-10-11 baseline took five runs. If the same few calls keep failing, stop and note them in the ADR.
Limits live in `configs/models.yaml`; update them from the providers' consoles when they change.

**The eval cache** is a SQLite file at `C:\dev\cache\chaouch\eval_cache.sqlite` (`cache_path` in
`configs/eval.yaml`), outside the repo and OneDrive. It stores every answer and judge call, keyed by the
provider and the exact request (model, prompt, parameters). The same request is never paid twice; a changed
prompt or model makes new calls. It is for development runs only; the app never uses it. It is safe to
delete, but the next run makes every call again.

**Reports** go to `reports/`: `<date>_<system>.json` (per-question results) and `<date>_baseline.md` (the
table). Smoke reports are ignored by git. Commit only the reports of a complete full baseline; the date is
the day of the final, complete run. A changed judge, judge prompt or gold-set version makes numbers
incomparable with older reports: re-run every system you want to compare.

## 4. Re-running the judge calibration

Do this after any change to the judge model or its prompts, before trusting new numbers
(spec 8.2; details in `data/evals/calibration/README.md`).

1. `uv run tasks.py calibrate` re-judges the 38 calibration answers (samples A and B) with the current
   judge: ~70 calls, ~20 min on Gemma. It prints per-sample agreement, a check on the B2 (Gemini) answers,
   and every disagreement with the judge's one-line reason.
2. Pass (exit code 0) = on each sample, fact agreement ≥ 80% and dialect within ±1 ≥ 80%.
3. Pass: record the numbers in an ADR. Fail: read the disagreements before changing a prompt.
4. `uv run tasks.py calibrate --cached` re-prints the report from the cache with no judge calls, e.g.
   after changing a grade in the sheets. `calibrate-report` shows the stored v1 judge results.

The grader's values are in the two sheets under `data/evals/calibration/`. The rule is the core-claim rule
(ADR 0009): a fact is present if its core claim is stated; a missing minor detail is fine, a wrong value is
not.

## 5. The main local model

Falcon-H1 3B Instruct, with Qwen3.5 2B as fallback ([ADR 0011](decisions/0011-main-local-model.md)). To
compare a new candidate: add it to `configs/models.yaml` and as `B0_<name>` / `B1_<name>` systems in
`configs/eval.yaml`, run `eval-full --systems B0_<name>,B1_<name>`, and compare B1 correctness and dialect
first (overall and by script), then latency, fine-tuning support (Phase 4) and B0.

## 6. Retrieval evaluation

`uv run tasks.py eval-retrieval` (after `db-up` and `index`; no LLM, no API calls, ~15 min on CPU,
mostly the reranker). It scores 7 configurations (BM25; dense, hybrid, hybrid + rerank for each
embedder) on two corpora, `core` (the procedure documents) and `full` (plus the distractors), and writes
`reports/<date>_retrieval.json` and `.md`. R@k counts the gold documents in the top k chunks; MRR uses
the rank of the first chunk from a gold document. Models stay on CPU; only one is in memory at a time.
